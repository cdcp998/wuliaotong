# 物料通管理系统 —— 开发规范（严格流程）

> 本规范是开发的**强制约束**。所有开发工作必须遵守，任何偏差需记录原因。

## 1. 开发总原则

1. **设计先行**：先改设计文档（《需求大纲.md》《数据库设计.md》《后端API设计.md》《前端设计.md》《开发排期.md》），评审通过后再写代码；代码与设计不一致视为缺陷。
2. **小步提交**：每个功能点一个提交，提交信息规范（见 §3），禁止大而全的一次性提交。
3. **阶段门禁**：按《开发排期.md》的 P0-P8 阶段推进；每阶段结束必须通过验收（演示 + 验证清单）才能进入下一阶段。
4. **可验证**：任何代码变更必须有对应的验证方式（接口测试/构建/运行检查），禁止"写完了但没验证"。

## 3. Git 流程

- 分支：`main`（稳定，只接受经过验证的提交）+ `dev`（日常开发）+ `feature/xxx`（功能分支）
- 提交信息格式：`类型(范围): 描述`，类型：`feat` `fix` `docs` `refactor` `test` `chore`，例：`feat(auth): 实现登录/登出/me 接口`
- 提交前必须：`git status` 确认无遗漏、无敏感信息（密码/Key）
- 版本号与 tag 规则见 §9（每个功能里程碑收尾必须同步版本并打 tag）

## 4. 后端规范

1. **Python 3.13**（生产部署目标 3.11+，代码保持兼容）；依赖用 `requirements.txt`（锁定大版本），虚拟环境 `backend/.venv`（不提交）。
2. **FastAPI + SQLAlchemy 2.x**；ORM 模型字段与《数据库设计.md》一一对应，表名/字段名必须一致。
3. **统一响应**：`{"code": 0, "message": "ok", "data": ...}`；错误码遵守《后端API设计.md》§11.8（4001-5003），禁止自造错误码。
4. **认证**：Session 存 `sys_session` 表；Cookie `session_id`，HttpOnly；依赖注入 `get_current_user` / `require_permission("code")`。
5. **库存事务铁律**：一切库存变动必须走 `services/stock.py` 的 `post_stock_change()`（行锁 + 单事务），禁止在路由里直接改库存表。
6. **类型标注**：所有函数必须有类型标注；Pydantic schema 校验入参；金额/数量用 Decimal，接口传字符串。
7. **写操作必须记操作日志**（`sys_operation_log`，中间件统一处理）。
8. **定时任务**：APScheduler，统一在 `app/scheduler.py` 注册。
9. **ORM 变更流程**：改《数据库设计.md》→ 改 `sql/init.sql` → 改 models → 写迁移说明（P0-P8 阶段无正式迁移工具，开发期允许重建库，上线后用备份恢复）。
10. **Redis 缓存规范**：一律走 `app/core/cache.py` 工具（禁止裸连 redis）；key 前缀 `wlt:`；读路径用 `cache_aside`，**写操作必须显式失效对应缓存**（与事务同函数内、commit 之后调用）；Redis 不可用必须静默降级直查数据库，禁止向请求路径抛异常；新增缓存需同步更新《数据库设计.md》决策 12 缓存清单。

## 5. 前端规范

1. **TypeScript strict**；组件用函数组件 + hooks，不写 class 组件。
2. 目录：`apps/*/src/{pages,components,routes,layouts}`；shared 包 `{api,types,stores,components,utils}`。
3. 服务端数据**只通过 shared 的 api client + store actions** 获取，禁止页面内散写 fetch。
4. 表单草稿存 store（页面切换不丢）；路由按权限过滤；按钮权限用 `hasPerm(code)`。
5. 命名：组件 PascalCase，hook `useXxx`，常量 UPPER_SNAKE，类型 `I` 前缀不用，直接语义名。
6. 移动端触屏目标 ≥44px；图片上传必须前端压缩（长边≤1600）。

## 6. 验证门禁（每项功能完成的硬性条件）

| 级别 | 内容 | 通过标准 |
|---|---|---|
| L1 语法/类型 | 后端 `python -m compileall`；前端 `tsc --noEmit` | 零错误 |
| L2 接口 | pytest 接口测试（认证/权限/事务回滚） | 全部通过 |
| L3 运行 | uvicorn 启动无异常；`/health` 返回 ok；登录联调 curl 走通 | 实测通过 |
| L4 前端 | 两端 `vite build` 成功；登录页联调真实 API | 构建+联调通过 |
| L5 阶段验收 | 按排期演示 + 走查清单 | 演示通过 |

- 任何提交前至少过 L1 + L3；P 阶段收尾必须过 L5。

### 6.1 测试执行分层策略（2026-08-08 起）

**原则**：普通改动只跑与本次修改相关的**针对性测试**；只有发布、主干构建、关键变更才跑**全量测试**。测试用例本身不变，仅控制触发时机与执行范围。

| 场景 | 执行范围 | 命令 |
|---|---|---|
| 普通改动（默认） | 按 git diff 自动映射相关测试（如改 `app/api/auth.py` → `test_auth.py + test_auth_ext.py`；改 desktop 页面 → desktop `tsc`；shared 包 → 两端 `tsc`） | `scripts/run_tests.sh` |
| 指定文件 | 只跑指定测试文件 | `scripts/run_tests.sh --files="tests/test_auth.py"` |
| 纯文档/配置（README、AI开发文档、*.bat 等） | 无需测试（脚本自动跳过） | 同上 |
| **发布（打 tag / 版本收尾）、主干构建（CI main）、关键变更、无法映射的新改动** | **全量**：后端 compileall + pytest 全量 + 前端两端 typecheck + build | `scripts/run_tests.sh --full`（CI 自动执行） |

**关键变更清单（命中任一 → 必须全量）**：`app/models/**`、`sql/*.sql`、`app/db.py`、`app/config.py`、`app/main.py`、`app/scheduler.py`、`app/core/**`、`app/services/stock.py`（库存事务铁律）、`app/api/init.py`（安装流程）、`backend/scripts/**`、`backend/requirements.txt`、`frontend/package.json/lock`、`scripts/**`（测试基础设施）。

**安全回退**：变更文件无法映射到具体测试（新模块/未知路径）时脚本自动升级为全量，禁止"只跑能跑的、跳过没把握的"。

**CI（.github/workflows/ci.yml）**：PR → 针对性测试（与目标分支 diff）；main 推送 / `v*` tag / 手动触发 → 全量测试。

**命令速查**：`scripts/run_tests.sh --dry-run` 预览本次将执行的测试范围；`--backend-only` / `--frontend-only` 只处理单端；`--changed="文件列表"` 显式指定变更（CI 用）。
- 测试失败、构建失败**不允许提交**，不允许"跳过验证先提交"。

## 7. 数据与安全红线

1. 密码 bcrypt 哈希存储，禁止明文；禁止在代码/提交中写数据库密码、API Key（用环境变量 `.env`，`.env` 进 `.gitignore`）。
2. 禁止 `DELETE` 物理删除业务数据（用状态位）；禁止绕过事务直接 UPDATE stk_stock。
3. 大模型 API Key 只存 `sys_config`，接口返回时脱敏。
4. 生产（外网）必须 HTTPS；Session Cookie Secure 标志。

## 8. 定义完成（Definition of Done）

一个功能点完成的判定：代码实现 ✅ + L1~L4 验证 ✅ + 设计文档同步 ✅ + 提交规范 ✅ + 无遗留 TODO/FIXME。

## 9. 版本管理（SemVer 2.0）

1. **版本格式**：语义化版本 `MAJOR.MINOR.PATCH`，git tag 加 `v` 前缀（如 `v0.1.0`）。
   - **MAJOR**：破坏性变更（API 不兼容、数据库结构不兼容、架构调整）
   - **MINOR**：向后兼容的新功能（功能里程碑/阶段收尾）
   - **PATCH**：Bug 修复、文档、非功能性调整
   - 开发期 0.x：`0.x.y`；首个正式发布 1.0.0。
2. **单一事实源**：`backend/app/__init__.py` 的 `__version__` 是全仓唯一版本源，所有其他位置只同步、不自行定版。
3. **必须同步的位置**（升级版本时缺一不可）：
   - `backend/app/__init__.py`（事实源，改这里）
   - `frontend/package.json`、`frontend/apps/desktop/package.json`、`frontend/apps/mobile/package.json`、`frontend/packages/shared/package.json`（4 处值必须与事实源一致）
   - `backend/app/main.py` 的 FastAPI `version`（统一用 `version=__version__`，随事实源自动跟随、无需手改）
   - `GET /api/v1/health` 的 `version` 字段（自动读取事实源，无需手改）
   - 前端 UI 版本展示（登录/我的/系统设置页）由 Vite 构建注入 `__APP_VERSION__`（vite.config.ts 读取本包 `package.json.version`），随 4 处 package.json 自动跟随、无需手改
   - git tag `v<版本号>`（打在同一提交上）
4. **升级流程**：确定新版本号 → 修改事实源 + 同步 4 个 package.json → 过验证门禁（§6）→ 提交 → 打 tag `v<版本号>`。
5. **一致性校验**（提交前必跑，任一不通过禁止提交；`scripts/run_tests.sh` 已内置为门禁）：
   - `python scripts/check_version.py`（自动化统一校验）：前端 4 个 package.json 与事实源一致、`main.py` 用 `version=__version__`（无硬编码）、前端 src 无硬编码版本号、`test_health` 存在；退出码 0 才通过
   - `pytest backend/tests/test_auth.py::test_health`：断言 `health.version == __version__`
   - （原 `grep` 对比为自动化脚本的等价落地，已并入 `scripts/check_version.py`）
6. **当前版本**：`v0.2.0`（2026-08-22 起；0.1.0 为 2026-08-07 基线，0.2.0 为线缆和设备插件 P0-P6 功能里程碑）。

## 10. 模块开发规范（插件，2026-08 起）

> 依据《线缆和设备插件开发方案.md》附录「开发规范补充（模块开发）」，随模块插件机制落地为强制约束。

1. 所有新功能模块化，源码写 `backend/modules/{code}/`（git 入库）；运行时目录 `backend/app/modules/` 由 `scripts/build_modules.py` 生成，**禁止手工修改**（已 gitignore）。
2. 模块 SQL 自带 `sql/install.sql` + `sql/migrations/`，**禁止把模块表加入核心 init.sql**；install.sql 作为 baseline（version='baseline'）纳入 checksum。
3. **卸载绝不删表删数据**；模块 SQL 禁止 `DROP TABLE`；CREATE/INSERT 必须幂等（IF NOT EXISTS / WHERE NOT EXISTS / INSERT IGNORE）。
4. 生命周期钩子（on_install/on_enable/on_disable/on_uninstall）必须幂等、可重入、异常安全；签名固定 `(db: Session, module: ModuleDef, ctx: ModuleContext)`。
5. Migration 必须使用核心工具函数（`app/core/migration_utils.py` 的 table_exists/column_exists/index_exists）保证幂等；每个 migration 文件只含一条 DDL，或由 `ModuleDef.migration_executors` 提供 Python 执行函数；**禁止修改已发布 migration/install.sql**（checksum 拦截）；失败恢复=追加幂等新迁移。
6. 模块间**禁止跨模块 import models**；跨模块数据访问走模块公开服务（如 `cable.services.fault_sync` / `knowledge.services.article_search`）或共享 core 层。
7. 模块权限点、菜单必须带 `module_code`（停用时自动失效/隐藏）；接口在 router 级挂 `require_module_enabled(code)`（未启用 4009/HTTP 403）。
8. 跨模块 API 变更必须主版本升级并更新依赖方 `depends`；依赖不满足 → 模块 ERROR（不允许静默不一致）。
9. 模块升级完成后必须**重启后端进程**才加载新代码（管理界面强制提示）。
10. 瓦片/缓存清理统一走 `tile_cache.py` 入口（worker 与清理接口共用进程锁，互斥）。
11. 模块后台任务经 `ModuleDef.jobs/workers` 注册（scheduler tick 检查 ENABLED，异常隔离），禁止在核心 scheduler 里直接注册模块任务。
