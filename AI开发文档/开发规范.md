# 物料通管理系统 —— 开发规范（严格流程）

> 本规范是开发的**强制约束**。所有开发工作必须遵守，任何偏差需记录原因。

## 1. 开发总原则

1. **设计先行**：先改设计文档（《需求大纲.md》《数据库设计.md》《后端API设计.md》《前端设计.md》《开发排期.md》），评审通过后再写代码；代码与设计不一致视为缺陷。
2. **小步提交**：每个功能点一个提交，提交信息规范（见 §3），禁止大而全的一次性提交。
3. **阶段门禁**：按《开发排期.md》的 P0-P8 阶段推进；每阶段结束必须通过验收（演示 + 验证清单）才能进入下一阶段。
4. **可验证**：任何代码变更必须有对应的验证方式（接口测试/构建/运行检查），禁止"写完了但没验证"。

## 2. 目录结构（严格遵守）

```
G:\phpstudy_pro\进销存\
├─ docs/ 或根目录          # 设计文档（.md）
├─ backend/                # FastAPI 后端（Python 3.13）
│  ├─ app/

│  │  ├─ config.py         # 配置（env 读取）

│  │  ├─ api/              # 路由（按模块一个文件：auth.py、products.py...）
```

## 3. Git 流程

- 分支：`main`（稳定，只接受经过验证的提交）+ `dev`（日常开发）+ `feature/xxx`（功能分支）
- 提交信息格式：`类型(范围): 描述`，类型：`feat` `fix` `docs` `refactor` `test` `chore`，例：`feat(auth): 实现登录/登出/me 接口`
- 提交前必须：`git status` 确认无遗漏、无敏感信息（密码/Key）
- 版本号与 tag 规则见 §9（每个功能里程碑收尾必须同步版本并打 tag）

## 4. 后端规范

1. **Python 3.13**（生产部署目标 3.11+，代码保持兼容）；依赖用 `requirements.txt`（锁定大版本），虚拟环境 `backend/.venv`（不提交）。
2. **FastAPI + SQLAlchemy 2.x**；ORM 模型字段与《数据库设计.md》一一对应，表名/字段名必须一致。
3. **统一响应**：`{"code": 0, "message": "ok", "data": ...}`；错误码遵守《后端API设计.md》§11.8（4001-5003），禁止自造错误码。
4. **认证**：Session 存 `sys_session` 表；Cookie `session_id`，HttpOnly；依赖注入 `get_current_user` / `require_permission("code")`。
5. **库存事务铁律**：一切库存变动必须走 `services/stock.py` 的 `post_stock_change()`（行锁 + 单事务），禁止在路由里直接改库存表。
6. **类型标注**：所有函数必须有类型标注；Pydantic schema 校验入参；金额/数量用 Decimal，接口传字符串。
7. **写操作必须记操作日志**（`sys_operation_log`，中间件统一处理）。
8. **定时任务**：APScheduler，统一在 `app/scheduler.py` 注册。
9. **ORM 变更流程**：改《数据库设计.md》→ 改 `sql/init.sql` → 改 models → 写迁移说明（P0-P8 阶段无正式迁移工具，开发期允许重建库，上线后用备份恢复）。
10. **Redis 缓存规范**：一律走 `app/core/cache.py` 工具（禁止裸连 redis）；key 前缀 `wlt:`；读路径用 `cache_aside`，**写操作必须显式失效对应缓存**（与事务同函数内、commit 之后调用）；Redis 不可用必须静默降级直查数据库，禁止向请求路径抛异常；新增缓存需同步更新《数据库设计.md》决策 12 缓存清单。

## 5. 前端规范

1. **TypeScript strict**；组件用函数组件 + hooks，不写 class 组件。
2. 目录：`apps/*/src/{pages,components,routes,layouts}`；shared 包 `{api,types,stores,components,utils}`。
3. 服务端数据**只通过 shared 的 api client + store actions** 获取，禁止页面内散写 fetch。
4. 表单草稿存 store（页面切换不丢）；路由按权限过滤；按钮权限用 `hasPerm(code)`。
5. 命名：组件 PascalCase，hook `useXxx`，常量 UPPER_SNAKE，类型 `I` 前缀不用，直接语义名。
6. 移动端触屏目标 ≥44px；图片上传必须前端压缩（长边≤1600）。

## 6. 验证门禁（每项功能完成的硬性条件）

| 级别 | 内容 | 通过标准 |
|---|---|---|
| L1 语法/类型 | 后端 `python -m compileall`；前端 `tsc --noEmit` | 零错误 |
| L2 接口 | pytest 接口测试（认证/权限/事务回滚） | 全部通过 |
| L3 运行 | uvicorn 启动无异常；`/health` 返回 ok；登录联调 curl 走通 | 实测通过 |
| L4 前端 | 两端 `vite build` 成功；登录页联调真实 API | 构建+联调通过 |
| L5 阶段验收 | 按排期演示 + 走查清单 | 演示通过 |

- 任何提交前至少过 L1 + L3；P 阶段收尾必须过 L5。
- 测试失败、构建失败**不允许提交**，不允许"跳过验证先提交"。

## 7. 数据与安全红线

1. 密码 bcrypt 哈希存储，禁止明文；禁止在代码/提交中写数据库密码、API Key（用环境变量 `.env`，`.env` 进 `.gitignore`）。
2. 禁止 `DELETE` 物理删除业务数据（用状态位）；禁止绕过事务直接 UPDATE stk_stock。
3. 大模型 API Key 只存 `sys_config`，接口返回时脱敏。
4. 生产（外网）必须 HTTPS；Session Cookie Secure 标志。

## 8. 定义完成（Definition of Done）

一个功能点完成的判定：代码实现 ✅ + L1~L4 验证 ✅ + 设计文档同步 ✅ + 提交规范 ✅ + 无遗留 TODO/FIXME。

## 9. 版本管理（SemVer 2.0）

1. **版本格式**：语义化版本 `MAJOR.MINOR.PATCH`，git tag 加 `v` 前缀（如 `v0.1.0`）。
   - **MAJOR**：破坏性变更（API 不兼容、数据库结构不兼容、架构调整）
   - **MINOR**：向后兼容的新功能（功能里程碑/阶段收尾）
   - **PATCH**：Bug 修复、文档、非功能性调整
   - 开发期 0.x：`0.x.y`；首个正式发布 1.0.0。
2. **单一事实源**：`backend/app/__init__.py` 的 `__version__` 是全仓唯一版本源，所有其他位置只同步、不自行定版。
3. **必须同步的位置**（升级版本时缺一不可）：
   - `backend/app/__init__.py`（事实源，改这里）
   - `frontend/package.json`、`frontend/apps/desktop/package.json`、`frontend/apps/mobile/package.json`、`frontend/packages/shared/package.json`（4 处值必须与事实源一致）
   - `GET /api/v1/health` 的 `version` 字段（自动读取事实源，无需手改）
   - git tag `v<版本号>`（打在同一提交上）
4. **升级流程**：确定新版本号 → 修改事实源 + 同步 4 个 package.json → 过验证门禁（§6）→ 提交 → 打 tag `v<版本号>`。
5. **一致性校验**（提交前必跑，任一不通过禁止提交）：
   - `grep -h '"version"' frontend/package.json frontend/apps/desktop/package.json frontend/apps/mobile/package.json frontend/packages/shared/package.json | sort -u`：输出必须只有一行，且等于事实源版本
   - `pytest backend/tests/test_auth.py::test_health`：断言 `health.version == __version__`
6. **当前版本**：`v0.1.0`（2026-08-07 起启用版本管理）。
