## 0. 结论摘要（TL;DR）

| 项 | 结论 |
|---|---|
| 接入方式 | **模块插件**：模块**源码**在 `backend/modules/{模块}/`（含自带 `sql/install.sql`），**由管线（scripts/build_modules.py）在测试/部署时安装到 `backend/app/modules/`** 供运行时加载。**可安装/卸载/停用**：接口 403 + 菜单隐藏 + 定时任务跳过，无需改核心代码；**卸载不删表不删数据**（数据红线），重装幂等续用 |

## 2. 模块插件机制（核心基础，先行实施）

> 用户要求"新的功能使用模块插件方式接入，可以停用"。此为**平台级基础能力**（P0），先落地，再在其上开发线缆各模块。

### 2.1 设计目标

1. **新增功能不侵入核心**：线缆/设备/任务/知识库全部代码落在各自模块包内，核心只提供插件框架。
2. **生命周期严格三分（v2.0 修正）**：**源码存在 ≠ 模块已安装 ≠ 模块已启用**。启动**不自动安装**；「安装」与「启用」都必须是管理员在「安装模块」界面**明确触发**。生命周期：`不存在 → 已部署 → 未安装 → 已安装(停用) → 已安装(启用)`，异常时进入 `ERROR`。
3. **可安装/卸载（SQL 由模块自带）**：模块包内携带 `sql/install.sql` + `sql/migrations/`（正式 migration runner，逐版本记录），**核心 init.sql 不含模块表**；「卸载/移除」= **不删除任何表与数据**（数据红线），仅注销，数据完整保留，重装幂等续用。
4. **安全默认 fail-closed**：模块权限判定**禁止 fail-open**——Redis 异常回源 MySQL、MySQL 也异常则**拒绝**模块访问（核心系统可 fail-open，模块权限不能）。
5. **可升级（锁版本 + checksum）**：模块独立 SemVer；manifest 带 `checksum/source_commit/build_id`，检测"版本一致但代码被改"的漂移。
6. **模块异常隔离**：生命周期 hook（安装/启用/停用/卸载/启动/关闭）异常 → 记日志 + 模块进入 `ERROR`（记录 last_error），**核心继续运行**。
7. **不破坏现有不变量**：现有核心（库存事务、认证、审计、Redis 降级等）一行不动。

### 2.2 后端：模块注册表 + 模块包 + 插件加载器

**新增核心表 `sys_module`（入 `init.sql` 核心段）**：

```sql
CREATE TABLE sys_module (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  code        VARCHAR(50)  NOT NULL COMMENT '模块编码，如 cable',
  name        VARCHAR(100) NOT NULL COMMENT '模块名称',
  version     VARCHAR(20)  NOT NULL DEFAULT '1.0.0' COMMENT '插件版本号（模块独立版本管理，SemVer，不受核心版本约束）',
  state       VARCHAR(20)  NOT NULL DEFAULT 'NOT_INSTALLED'
              COMMENT 'NOT_INSTALLED 未安装/INSTALLING 安装中/INSTALLED 已安装(未启用)'
                    '/ENABLED 已启用/DISABLED 已停用/ERROR 异常/UPGRADING 升级中',
  schema_version VARCHAR(20) NOT NULL DEFAULT '0' COMMENT '已执行的模块 SQL 结构版本（migration 序号）',
  depends     JSON         NULL COMMENT '依赖约束（JSON 数组，如 ["cable>=1.2.0","task>=0.5.0"]；SemVer 校验）',
  config      JSON         NULL COMMENT '模块配置（JSON，如地图源/最大缩放/下载并发；敏感字段脱敏）',
  description VARCHAR(255) NOT NULL DEFAULT '',
  last_error  VARCHAR(500) NOT NULL DEFAULT '' COMMENT '最近异常信息（ERROR 态）',
  last_error_at DATETIME   NULL COMMENT '最近异常时间',
  installed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='功能模块注册表（模块插件机制）';
```

**新增核心表 `sys_module_migration`**（migration 执行记录，入 init.sql 核心段）：

```sql
CREATE TABLE sys_module_migration (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_code VARCHAR(50)  NOT NULL COMMENT '→ sys_module.code',
  version     VARCHAR(50)  NOT NULL COMMENT 'migration 标识（如 0001_initial / 0002_add_xxx）',
  checksum    VARCHAR(64)  NOT NULL DEFAULT '' COMMENT 'migration 文件 sha256（篡改检测）',
  success     TINYINT      NOT NULL DEFAULT 1 COMMENT '1 成功 / 0 失败',
  executed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_module_version (module_code, version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='模块 migration 执行记录';
```

**模块独立版本管理 + 锁版本（已确认 2026-08）**：
- 每个模块**独立版本号**（SemVer，如 cable 1.2.0 / task 0.3.1），**不受核心/前后端版本约束**——现有 `scripts/check_version.py` 只强制核心前后端版本一致，**模块版本独立不参与该校验**。
- 版本单一事实源 = `backend/modules/{code}/__init__.py::ModuleDef.version`；管线安装时生成 `backend/app/modules/manifest.json`，内含 `{code, version, schema_version, build_id, source_commit, checksum}`（**checksum=模块包文件 sha256**，用于发现"版本号一致但代码被篡改"）。
- `GET /modules` 返回 `version`（库内插件版本号）+ `source_version`（manifest 版本）+ `source_checksum`，安装模块界面据此做三处版本漂移与代码漂移提示。
- 依赖约束正式 SemVer：`depends` 为 JSON 数组，元素 `"code>=x.y.z"`（支持 `>=`/`<`/`==`/`^`），启用/安装前由核心 SemVer 校验器比对已安装模块版本，不满足 → 拒绝。

**扩展 `sys_menu`**：新增 `module_code VARCHAR(50) NOT NULL DEFAULT ''`（该菜单归属模块；空=核心菜单）。非 ENABLED 模块的菜单树整体隐藏。

**模块 SQL 自包含 + 正式 migration（v2.0 修正）**：每个模块包内携带 `sql/install.sql`（基线建表 + 种子，幂等：`CREATE TABLE IF NOT EXISTS` + `INSERT ... ON DUPLICATE KEY UPDATE`/`INSERT IGNORE`）与 `sql/migrations/{NNN}_{name}.sql`（版本化增量，如 `0001_initial.sql`/`0002_add_xxx.sql`）。**核心 init.sql 只建核心表（含 sys_module / sys_module_migration），不建任何模块表**；模块表结构以模块 SQL 为唯一事实来源。**migration runner（`app/core/modules.py::MigrationRunner`）**：安装时执行 install.sql（若从未执行）→ 按序执行 `> 当前 schema_version` 的 migration → **每个 migration 单独校验 checksum 并记录到 sys_module_migration**（成功/失败各自记录，失败不再重复执行）→ 更新 schema_version。**不承诺 DDL 整体回滚**（MySQL DDL 非事务），每个 migration 独立、可重入、幂等。

> **开发与运行分离**：开发只在 `backend/modules/` 写模块源码；**运行时加载的是 `backend/app/modules/`**（管线生成）。测试/部署前跑 `scripts/build_modules.py`，把源码复制进 `app/modules` 并生成 manifest（含 checksum）。`backend/app/modules/` 加入 `.gitignore`（构建产物），模块版本以源码 git 为准。

**ModuleDef 契约（v2.0 增补生命周期钩子）**（`app/core/modules.py`；模块源码运行时以 `from app.core.modules import ModuleDef` 引用）：

```python
@dataclass
class ModuleDef:
    code: str                     # 如 "cable"
    name: str
    version: str                  # SemVer，独立版本管理
    router: APIRouter             # 该模块全部接口（统一加依赖 require_module_enabled(code)）
    dependencies: list[str] = []  # 🆕 依赖约束（SemVer，如 ["cable>=1.2.0"]）
    audit_labels: dict[str, str] = {}
    install_sql: list[str] = []   # 安装时执行的 SQL 文件（相对模块包，如 ["sql/install.sql"]）
    migrations_dir: str = "sql/migrations"   # 🆕 migration 目录（正式 runner 读取）
    # 🆕 生命周期钩子：每个 hook 异常 → 记日志 + 模块 state=ERROR + last_error，核心继续运行
    on_install: Callable | None = None      # 安装后（SQL 已执行）
    on_enable: Callable | None = None       # 启用后
    on_disable: Callable | None = None      # 停用后
    on_uninstall: Callable | None = None    # 卸载后（不删数据）
    jobs: list[Callable] = []               # APScheduler job 工厂（每次 tick 检查 ENABLED）
    workers: list[Callable] = []            # 🆕 后台 worker 工厂（如瓦片下载消费；异常隔离）
```

**安装管线**（`scripts/build_modules.py`，测试/部署前执行，幂等；**只负责构建，不触碰数据库**）：

```
build_modules() 过程：
1. 扫描 backend/modules/ 各子目录（每个=一个模块 code）
2. 逐模块校验结构（存在 __init__.py 且定义 ModuleDef）→ 复制到 backend/app/modules/{code}/
3. 生成 backend/app/modules/__init__.py + manifest.json
   （{code, version, schema_version, build_id, source_commit, checksum=sha256(模块文件)}）
4. 清理源码中已删除模块在 app/modules 的旧目录（与源码保持一致）
5. 对复制后的模块源码做 compileall 校验（L1 门禁前置）
调用方：scripts/run_tests.sh（测试前自动执行）与部署脚本；不依赖手工复制
```

**加载器（v2.0 修正：启动不自动安装）**（`app/core/modules.py::register_modules(app)`，main.py 替换静态注册为该机制，核心路由保持现状）：

```
register_modules(app) 过程：
1. 启动时读 sys_module（表不存在/未初始化 → 静默跳过，保证安装向导可用）
2. 遍历 app/modules/ 下所有 ModuleDef（运行时安装目录，管线已就绪）：
   - 未在 sys_module 记录 → 插入 state=NOT_INSTALLED 记录（仅登记，不执行 SQL、不挂路由）
   - state=NOT_INSTALLED → 不挂载（等待管理员「安装」）
   - state=ENABLED 且依赖满足 → app.include_router(router, prefix=api_prefix)
   - 其余状态（INSTALLED/DISABLED/ERROR/INSTALLING/UPGRADING）→ 不挂载
   - 合并 audit_labels 到 _AUDIT_MODULES；注册 scheduler jobs/workers（tick 时校验 ENABLED）
3. 提供 GET /modules（安装模块界面用）与运行期状态缓存（Redis wlt:module:{code}，TTL 30s）
```

**模块生命周期状态机（v2.0 修正：安装/启用均由管理员触发）**：

```
不存在(无记录) → [加载器扫描到源码] → NOT_INSTALLED(未安装)
NOT_INSTALLED → [管理员「安装」→ MigrationRunner 执行 install.sql + migrations] → INSTALLED(已安装/停用)
INSTALLED → [管理员「启用」→ on_enable] → ENABLED(已启用)
ENABLED → [管理员「停用」→ on_disable] → DISABLED(已停用)
任何态 → [hook/SQL 异常] → ERROR(记录 last_error/last_error_at；可修复后重试)
ENABLED → [升级：version/schema 变更 → MigrationRunner 应用新 migration] → UPGRADING → ENABLED
DISABLED/INSTALLED → [管理员「卸载」→ on_uninstall，不删表不删数据] → NOT_INSTALLED（表仍在，数据保留）
```

**安装 / 卸载（移除）语义（关键，SQL 由模块自带 + 正式 migration）**：

| 动作 | 做什么 | 不做什么 |
|---|---|---|
| **安装**（首次或重装） | 管理员明确触发：`MigrationRunner` 执行 install.sql（幂等建表+种子）→ 按序应用 `>schema_version` 的 migration（逐条校验 checksum、记录 `sys_module_migration`）→ `state=INSTALLED` → 可「启用」 | 不删已有表/数据；**不承诺 DDL 整体回滚**（MySQL DDL 非事务），每个 migration 独立幂等可重入 |
| **启用/停用** | `state=ENABLED/DISABLED` + on_enable/on_disable 钩子；接口 403 按状态、菜单隐藏 | 不动 SQL、不动表、不动数据 |
| **升级** | version/schema 变更 → 跑管线 → `UPGRADING` → MigrationRunner 应用新 migration → `ENABLED`；checksum 不符 → 拒绝升级并告警 | 不删数据；升级失败回到原版本记录 |
| **卸载/移除** | 管理员明确触发：`state=NOT_INSTALLED` + on_uninstall；接口 403、菜单/权限下线、定时任务/worker 跳过 | **绝不 DROP TABLE / 删数据**——表结构与业务数据完整保留；重装幂等续用，历史数据不丢 |

> 与现有数据红线一致：禁止物理删除业务数据。模块卸载只做"功能注销"，数据库资源全部保留。

**停用语义（关键）**：

| 层 | 非 ENABLED 后行为 | 生效方式 |
|---|---|---|
| 接口 | 模块 router 统一挂 `Depends(require_module_enabled(code))`，非 ENABLED 返回 403「模块未启用」 | **立即**（每次请求查模块状态缓存） |
| 菜单 | `GET /menus` 过滤 `module_code` 非 ENABLED 的节点（含子级） | 立即 |
| 权限 | 非 ENABLED 模块的权限点不可勾选、已勾选的不产生效果 | 立即 |
| 定时任务/worker | job/worker 工厂每次 tick 检查 state==ENABLED，否则 return（队列保留，启用后续跑） | 下一 tick |
| 前端 | 路由守卫 `RequireModule(code)`：非 ENABLED → 「模块未启用」占位 | 刷新/拉取模块状态后 |

**fail-closed 判定（v2.0 修正，安全默认拒绝）**：

```
module_enabled(db, code)：
    Redis wlt:module:{code} 命中且 state==ENABLED → True
    Redis miss/异常 → 回源 MySQL sys_module.state==ENABLED → True
    MySQL 异常/无记录 → **False（拒绝模块访问）**
```
- 核心系统（登录/库存等）维持现有 fail-open 降级语义不变；**模块权限一律 fail-closed**。
- 唯一例外：初始化安装向导期间（sys_module 表不存在）→ 无模块，模块接口天然 404/403，不阻塞安装流程。

### 2.3 前端：模块状态 + 路由守卫 + 菜单过滤

- **共享层**（`packages/shared`）：新增 `moduleApi.getModules()`；`useAuthStore` 增加 `modules: Record<string, ModuleInfo>` 与 `moduleEnabled(code)`；登录后与菜单一起拉取。

### 2.5 模块开发规范（写入《开发规范.md》）

- 新功能**一律**以模块包实现：**源码写 `backend/modules/{code}/`**，禁止直接往核心 `app/api` 塞线缆相关路由；**运行时目录 `backend/app/modules/` 由管线（`scripts/build_modules.py`）生成，禁止手工修改**
- **开发流程**：改 `backend/modules/` → 跑 `scripts/build_modules.py`（构建进 `app/modules`，生成 manifest+checksum）→ 测试/构建（L1-L5）→ 提交源码（git 只管源码目录）
- 模块间不允许跨模块直接 import models；跨模块数据访问走对方 API 或共享 core 层
- **模块自带 SQL + 正式 migration**：每个模块必须提供 `sql/install.sql`（基线建表+种子，幂等）+ `sql/migrations/{NNN}_{name}.sql`（版本化增量）；**禁止把模块表加进核心 init.sql**；模块 SQL 是模块表结构的唯一事实来源；结构变更必须新增 migration 文件并递增 `schema_version`，**禁止修改已发布的 migration 文件**（用新 migration 演进）
- **卸载绝不删表删数据**：模块 SQL 里禁止出现 `DROP TABLE`（除非模块自带清理接口并二次确认）
- 生命周期钩子（on_install/on_enable/on_disable/on_uninstall）必须幂等、可重入、异常安全（异常会进入 ERROR 态但不得拖垮核心）
- 模块须自带：ModuleDef（含 dependencies/install_sql/migrations_dir/生命周期钩子）、pytest（模块目录 `tests/`，含 migration/生命周期用例）、文档段
- 停用/卸载/升级模块不得破坏核心启动与核心功能（核心加载器对模块异常做 try/except + 告警，模块故障不拖垮核心）

## 5. 关键架构决策（含对比与理由）

### 5.1 空间数据：保持 MySQL 单库 + 应用层 Geo 计算（不引入 PostGIS）

规划原文建议 "mysql + PostGIS"。**推荐不引入 PostgreSQL**：

| 对比 | PostGIS（引入 PG 第二库） | MySQL 单库 + 应用层 Geo |
|---|---|---|
| 部署/运维 | 需新增 PG 服务、Docker 编排、双库备份/迁移，破坏"MySQL 唯一事实来源" | 零新增服务，沿用现有备份/编排 |
| 数据规模 | 适合十万级要素+复杂空间分析 | 本场景线缆数百条 × 节点数百个 = 万级点，**应用层算力绰绰有余** |
| 距离/插值/投影 | ST_Length(geography)/ST_ClosestPoint 现成 | 纯 Python 约百行（Haversine+段插值+点投影），配 pytest 可测 |
| MySQL 8 现成能力 | — | `ST_Distance_Sphere`（球面米制距离）可辅助；`cable_point` 累计距离表免去重算 |
| 前端 | 仍需 GeoJSON 出站 | 后端直接返回 GeoJSON，Turf.js 交互 |

**决策**：线缆 `geometry` 存 GeoJSON JSON 列；`cable_point` 存逐点坐标+累计距离；距离/插值/最近点/剩余距离全部由 `backend/app/modules/cable/services/geo_math.py` 实现（纯函数、单测覆盖）。**隔离抽象**：API 输出统一 GeoJSON，未来若规模暴涨需换 PostGIS，仅替换 geo_math 内部实现，接口与前端不变。

**选型结论（2026-08 复核，定稿）**：**继续 MySQL 单库，不切换 PostgreSQL，也不引入 PG 第二库做混合**。理由：
1. **既有核心 100% MySQL**：物料通 44 张表、库存行锁事务（`post_stock_change`）、init.sql、CI mysql:8.0 服务、mysqldump 备份、Docker/Windows 生产——切换 PG = 全量重写 + 数据迁移风险，仓库域从 PG 得不到任何收益。
2. **地理数据量级极小**：线缆数百条 × 节点数百 = 万级点；`geo_math` 纯函数（Haversine/段插值/点投影）+ `cable_point` 累计距离表 + MySQL `ST_Distance_Sphere` 完全够用，且有 pytest 与 Turf 对拍锁口径。
3. **单库保住 §14 跨模块单事务铁律**：库存扣减 + 领用 + 任务 + 故障联动必须在同一事务；**引入 PG 第二库会打破跨库事务，是比"MySQL 应用层算地理"更坏的选择**（明确反对混合双库）。
4. **模块 migration runner 与数据库无关**：`sys_module_migration` + `sql/migrations` 自研 runner 在 MySQL 同样成立（评审第 3 项不构成换库理由）。
5. **保留逃生舱**：`geo_math` 已隔离抽象，未来若地理规模暴涨（整城拓扑/路径规划/高并发空间分析），可只把线缆 geo 服务迁到独立 PG+PostGIS，不动仓库核心——**现在换不划算，未来可局部换**。

### 5.2 地图引擎：Leaflet

- 用例=栅格瓦片底图（Esri）+ GeoJSON 矢量叠加 + 点击/绘制交互，Leaflet 轻量（~40KB）、成熟稳定、GeoJSON 一等公民；`react-leaflet` 与 React 19 集成顺滑。
- MapLibre GL 面向矢量瓦片/自定义样式，本项目无此需求，且包体更大。
- 备选：若后续需要 3D/高程/更炫样式再评估 MapLibre。

### 5.3 坐标系：统一 WGS84

- 存储与计算一律 **WGS84（EPSG:4326）**；Esri World Imagery 瓦片天然 WGS84，无偏移。
- 手机浏览器 `navigator.geolocation` 返回 WGS84，直接可用。
- 预留 `coord.py` 工具（WGS84↔GCJ-02 单向转换，标准偏移算法），**仅当**未来接高德/百度卫星源时在瓦片 URL 构造层使用；不改库内存储、不改前端坐标系。
- 若地图源与业务数据都走 WGS84（默认），则完全无需坐标转换。

### 5.4 瓦片缓存：后端瓦片代理（推荐）vs 前端 PWA 缓存

规划要求"前端优先读本地缓存，未命中请求在线源并按需缓存"。**推荐后端瓦片代理**：

```
前端(Leaflet) ── /map/tile/{z}/{x}/{y}（本域代理，同源无 CORS）──> 后端
后端：1) data/map/{source}/{z}/{x}/{y}.png 命中 → 直接返回
      2) 未命中 → 抓取 Esri 在线源 → 落盘 → 返回 → 写 map_download_task 成功
```

- 统一出口天然实现"优先读缓存+未命中按需缓存"，且规避浏览器跨域与在线源并发限制（服务端可控制并发/限速/UA）；
- 管理端"框选区域批量下载"复用同一落盘目录与同一代理读取逻辑，前后台缓存一致；
- 相比 PWA/ServiceWorker 缓存：无缓存淘汰策略复杂度、无需 PWA 安装、内网系统更可控；离线场景下已下载区域瓦片仍在磁盘，前端仍可浏览。
- 批量下载：`map_download_task` 入队 → Redis 队列（复用现有 Redis）→ 后台 worker 并发拉取（默认 4 并发，可配）→ 更新 `map_cache_region` 统计；断点续传靠 `uk(region_id,z,x,y)` 幂等 + 失败重试（retry_count≤3）。
- 瓦片清理：按区域删除磁盘文件 + 清理 `map_download_task` + 更新统计；支持"清理全部缓存"。

### 5.5 测距定位 / 故障导航：geo_math 服务 + Turf.js 前端 + Geolocation

- **长度**：保存线缆时后端用 geo_math 逐段 Haversine 累加写 `cable.total_length`；前端绘制时 Turf.js `turf.length()` 实时预览（口径一致：Haversine 球面距离）。
- **累计距离插值**：给定目标米数 D → `cable_point` 二分定位所在段 → 段内按长度比例线性插值经纬度（geo_math.interpolate_by_distance）。
- **反向输入**："距终点 120 米" → `total_length - 120` → 同一插值函数。
- **最近点投影**：用户位置 P → 对 `cable_point` 逐段求点到线段最近点（geo_math.project_to_line），取全局最近 → 返回投影点坐标 + 该点累计距离。
- **剩余距离**：投影点累计距离与目标故障点累计距离之差的绝对值（沿线路径距离）。
- **实时导航**：手机端 `navigator.geolocation.watchPosition`（高频 1s/低频 5s 可切）→ 前端每帧调用 `/geo/navigate`（或前端本地 Turf 计算，后端兜底）→ 地图实时更新用户位置/目标点/路径；接近 <50m 触发震动 + 语音播报。
- **一致性**：前后端都用 Haversine（R≈6371008.8m，与 turf 默认一致），交互计算用 Turf.js、权威计算（落库/导航）用后端 geo_math，两侧 pytest 对拍同一组样本坐标。

### 5.6 手机端提醒：Web 能力（免原生 App）

- `navigator.vibrate([300,100,300])`：接近故障点/新任务派发时震动（Android 支持；iOS Safari 不支持静默降级）。
- **Web Speech API**（`speechSynthesis.speak`）中文语音播报"前方约 30 米到达故障点"（移动端 Chrome/Safari 支持度好，需用户手势后初始化）。
- **实时推送（P2 可选）**：现有通知是 DB 轮询/刷新拉取；若要"派发即推"，加 WebSocket（`/ws/notify`）或 SSE，通知落库不变（`sys_notification` 仍为事实来源），推送仅作实时提示。
- 说明：Web 无法在后台/锁屏收推送；若未来需要，可评估"内网 Web 套壳（如 Tauri/Capacitor）或企业微信/钉钉 webhook"，方案预留 webhook 配置项（sys_config）。

### 5.7 知识库 AI 生成：复用 LLMClient + RAG-lite + 人工审核

- **生成链路**：维修任务/故障信息（故障类型、线缆类型、现象描述、物料清单）→ 检索已发布知识（按 related_fault_types/related_cable_types/tags 关键词匹配，取 Top-N 作上下文）→ 现有 `LLMClient` 文本槽位生成「维修步骤/配件清单/安全注意/常见排查」→ 落 `knowledge_article`（`author_type=ai`，`status=0 草稿`）→ 系统管理/知识库"待审核"列表人工编辑+发布。
- **不引入向量库**：本规模关键词+标签检索足够；向量 RAG（如 pgvector/ES）标 P2 可选。
- **物料关联自动建议**：AI 生成结果里抽取物料名 → 匹配 `base_product` → 写入 `knowledge_material_link` 建议（人工确认）。
- 大模型调用全走现有 `sys_llm_log` 日志，失败不影响主流程（人工编写兜底）。

### 5.8 设备管理（device 模块）

- **现用设备管理**：设备台账（编号/名称/型号/分类/部门/地点/坐标/在用状态/保修），CRUD + Excel 导入导出（沿用 base 模块风格）；设备坐标可在地图上标记（独立叠加层）。
- **设备维修任务**：与线缆维修任务同一套状态机/派发/记录/领用/通知流程，独立建表（`device_task`/`device_task_record`），复用**通用任务状态机核心**（见 §5.12），避免复制代码。
- 设备与知识库联动：设备分类/故障现象 → 推荐知识（复用 knowledge 模块检索能力）。

### 5.9 通知三渠道（站内 + 邮件 + 短信）

- 现有：站内通知 `sys_notification`（已读/未读/联动/删除）+ SMTP 邮件（系统设置已配）。
- 新增：**短信接口** `app/services/notify/sms.py::SmsClient`（服务商可配置：阿里云/腾讯云/容联云/通用 HTTP 网关），统一 `notify_user(...)` 分发。
- 派发任务/故障升级/预警等事件默认站内必达；**短信/邮件按事件类型配置**（如"紧急任务派发"强制短信+邮件），渠道失败降级不阻断。
- 发送记录：邮件/短信走 `sys_llm_log` 之外的独立日志或 `sys_notification` 扩展字段记录，避免丢消息；短信内容模板化（长度/签名合规）。

### 5.10 多地图源（MapSourceAdapter 抽象，v2.0 加强）

地图源注册表存 `sys_module.config.map_sources`（JSON 数组），默认内置 Esri World Imagery；管理页可新增/编辑/启停多源。**每个源实现一个 Adapter，禁止在 `MapView.tsx` 里堆坐标转换**。

**MapSourceAdapter 接口**（`backend/app/modules/cable/services/map_sources/base.py` + 前端 `geo.ts` 同构）：
```python
class MapSourceAdapter(ABC):
    type: str                       # esri/mapbox/google/amap/baidu/tms/wms/wmts/xyz
    def get_tile_url(self, z, x, y, api_key) -> str            # 瓦片 URL（后端代理持有 key）
    def get_tile_coordinate_system(self) -> str                # wgs84/gcj02/bd09
    def transform_business_geometry(self, geojson) -> geojson  # 业务坐标(库内WGS84) → 源坐标（仅显示层）
    def transform_click_coordinate(self, lat, lng) -> (lat, lng)  # 地图点击 → 回写 WGS84
    def transform_gps_coordinate(self, lat, lng) -> (lat, lng)    # 手机 GPS(WGS84) → 源坐标
    def validate_config(self, cfg) -> None                      # 配置校验
# 实现：EsriAdapter / AmapAdapter(gcj02) / BaiduAdapter(bd09) / GoogleAdapter / XYZAdapter /
#       TMSAdapter / WMSAdapter / WMTSAdapter
```
- **坐标转换链（明确，不再"看起来统一"）**：
  ```
  业务坐标(库内 WGS84) ──transform_business_geometry──▶ 源坐标系(WGS84/GCJ02/BD09) ──▶ 瓦片对齐显示
  地图点击/绘制 ──transform_click_coordinate──▶ WGS84 ──▶ 落库
  手机 GPS(WGS84) ──transform_gps_coordinate──▶ 源坐标系（导航叠加显示）
  ```
  每个源只依赖自己的 Adapter 转换，业务库内数据恒为 WGS84，互不污染。
- 转换实现：WGS84↔GCJ-02 标准偏移算法、GCJ-02↔BD-09 标准算法（后端 `coord.py` + 前端 `geo.ts` 同款，配 pytest 对拍）。
- 后端瓦片代理按 `{source}` 分目录缓存（`data/map/{source_key}/{z}/{x}/{y}.png`），各源缓存互不干扰；**代理隐藏 api_key**（key 只存在后端，前端只请求 `/map/tile/...`）。

**地图源配置契约（`sys_module.config.map_sources[]`）**：
```json
{
  "key": "amap", "name": "高德卫星图", "type": "amap",
  "url_template": "https://webst0{1-4}.is.autonavi.com/appmaptile?style=6&x={x}&y={y}&z={z}",
  "api_key": "…", "api_secret": "…(加密存储，永不下发前端)",
  "coordinate_space": "gcj02", "projection": "EPSG:3857",
  "min_zoom": 3, "max_zoom": 18,
  "tile_format": "png", "tile_size": 256,
  "rate_limit": 5, "concurrency": 4, "max_retry": 3,
  "cache_enabled": true, "cache_ttl": 86400,
  "attribution": "© 高德", "terms_url": "https://…",
  "enabled": true
}
```
- **安全**：`api_secret` 加密存储（复用 sys_config 脱敏模式），**任何 `/map/sources` 接口永不下发 secret**；瓦片代理持有 key 并遵循源的 rate_limit/concurrency/max_retry；429 限流退避重试、失败降级提示。
- 合规：`attribution` 必须展示（Leaflet 底图层强制叠加 attribution 控件），`terms_url` 存库备查；缓存仅限授权用途（内部系统）。
- `/map/sources/test` 用最小瓦片（z=0/0/0）验证 URL + key 可用性。

### 5.11 地图叠加层选择（避免数据过载）

- 地图组件内置**叠加层开关**（Leaflet `L.control.layers` + 前端 Store 持久化当前勾选）：线缆层 / 故障层 / 设备层（device 模块注册）/ 标记点层 / 缓存区域层 / 用户位置层。
- 每层可独立显隐；层内数据量大时支持按类型筛选 + 聚合（聚类点，P2 可选 `leaflet.markercluster`）。
- 叠加层注册机制：cable 模块暴露"地图工作台"可挂接的 layer 注册表，device 模块通过共享层注册"设备层"，实现跨模块叠加而不耦合代码。

### 5.12 通用任务状态机核心（task 与 device 共用，v2.0 修正）

- 核心服务 `backend/app/core/task_engine.py`（不建表，纯服务）：状态机白名单校验、流转、派发通知（三渠道+投递记录）、记录写入、领用链接（经 `TaskReferenceResolver`）。
- cable 的 `maintenance_task` 与 device 的 `device_task` 都调用该核心，各自持独立表与路由；避免两套状态机代码漂移。
- **状态机（v2.0 增 cancelled）**：`pending → assigned → in_progress → done → verified → closed`；`done→in_progress`（验收驳回）；**`pending/assigned → cancelled`（取消，必填 cancel_reason/cancelled_by/cancelled_at）**。
- **任务↔故障一致性（v2.0 修正：完成 ≠ 已修复）**：
  - `complete`（任务 done）→ 关联 `fault.status = 2 待验证`（**不直接标已修复**）
  - `verify`（任务 verified）→ `fault.status = 3 已修复`
  - `reject`（验收驳回）→ `fault.status = 1 处理中`
  - `cancelled` → 故障状态回退（若因本任务进入待验证 → 回到处理中）
- **取消约束**：已产生库存出库（task_requisition 关联且已过账）的任务**不能直接取消**，进入业务处理流程（提示先处理领用单）；仅 pending/assigned 可取消。
- **幂等**：任务状态流转等关键 POST 支持 `Idempotency-Key`（见 §14）。

### 8.3 角色合并与迁移

- **巡检人员**：规划中曾提出，最终**不建独立角色**，其能力（查看线缆/上报故障/查看知识）并入维修人员。
- **使用者**（内置 `user` 角色）：与维修人员合并——维修人员默认权限包含 `req:apply`/`stk:query`。存量「使用者」账号的处理：
  - 方案 A（推荐）：把存量 `user` 角色账号**迁移**到维修人员角色（`UPDATE sys_user SET role_id=(维修人员id) WHERE role_id=(user id)`），同时把 `user` 角色标记停用/保留兼容。
  - 方案 B：保留 `user` 角色不动（零迁移），仅新增维修人员用于新平台；两角色权限并存。
  - P0 采用**方案 B**（不动存量、不影响现有测试与业务）；P5 上线前按需做方案 A 迁移脚本（`scripts/migrate_user_to_maintenance.sql`）。
- 权限点分配沿用现有 `sys_role_permission` 机制，零改动；新角色/新权限点入 init.sql 种子（id 续排）。

### 8.4 数据范围（Data Scope，v2.0 新增：权限 ≠ 数据权限）

**数据范围枚举**：`ALL 全部 / DEPARTMENT 本单位 / OWN 本人 / ASSIGNED 被指派`。每个数据类目配置**功能权限 + 数据范围**两层：

| 数据类目 | 功能权限（谁能看/操作） | 默认数据范围 |
|---|---|---|
| 线缆 cable | cable:view / cable:manage | 调度员 ALL；维修人员 ALL（只读）；可选 DEPARTMENT |
| 故障 fault | fault:report / fault:manage | 调度员 ALL；维修人员：**自己上报 + 派给自己任务关联**的故障 |
| 维修任务 task | task:process / task:verify / task:dispatch | 维修人员 **ASSIGNED**（我的任务）；调度员 ALL |
| 设备 device | device:manage / device:task | 调度员 ALL；维修人员：本单位设备（DEPARTMENT，可配）或 ASSIGNED（派给自己的设备维修任务） |
| 知识 knowledge | knowledge:view / write / review | 已发布对全部可见；草稿仅作者 + 审核人 |

- **实现**：`app/core/data_scope.py` 提供 `scope_filter(db, user, entity, perm_code) -> SQLAlchemy 条件`，列表接口统一注入；**数据范围在服务层强制过滤**（不依赖前端传参），防止越权。
- 数据范围存 `sys_role` 扩展列 `data_scope JSON`（如 `{"task":"ASSIGNED","device":"DEPARTMENT"}`）或独立 `sys_role_data_scope` 表（P0 用角色扩展列，简单够用）。
- 默认值：超级管理员 ALL；调度员 ALL；维修人员 task=ASSIGNED、fault=OWN+ASSIGNED、device=DEPARTMENT。

> 作用：避免"维修人员 A 能看到全部线缆/设备/任务"的越权问题；权限测试阶段不再返工。

## 9. 技术实现要点

### 9.1 geo_math.py（纯函数，重点单测）

```python
# backend/app/modules/cable/services/geo_math.py
R = 6371008.8  # 与 turf 一致

def haversine(lat1, lng1, lat2, lng2) -> float          # 两点球面距离（米）
def cumulative_distances(points) -> list[float]          # 逐段累计（cable_point 写入用）
def interpolate_by_distance(points, dists, target) -> (lat, lng)  # 按米数插值（二分定位段）
def project_point_to_line(p, a, b) -> (lat, lng, t)      # 点到线段最近点（局部坐标近似 + 球面修正）
def project_to_polyline(points, p) -> (nearest_pt, cum_dist)   # 点到折线最近点+累计距离
def remaining_distance(from_cum, to_cum) -> float        # 沿线剩余距离
```

- 边界用例（pytest）：空点集/单点/超长距离/目标超出总长（夹取端点）/投影落在线段外（夹取顶点）/与 turf 结果对拍（同一坐标样本，误差 <1e-3m）。

### 9.2 瓦片下载 worker + 缓存容量保护（v2.0 加强）

- 依赖：现有 Redis + APScheduler。worker 循环：从队列（`wlt:tile-dl:{region}`，用 list/stream）取任务 → 校验模块 ENABLED → 抓取 → 落盘 → 更新统计；失败入重试队列（retry_count<3）。
- 并发限流：信号量默认 4（`sys_module.config.tile_concurrency`），对在线源保持礼貌（rate_limit/间隔/限速可配）。
- 幂等：`uk(region_id,z,x,y)`；文件已存在（size>0）直接标成功，支持断点续传（重复启动不重复下载）。
- **容量保护（v2.0，防止"框整个东京 z5~19"打爆磁盘/队列）**：
  - `cache.max_size`（默认 100GB）：全缓存超限 → 拒绝新下载任务并按 LRU 清理
  - `region.max_tiles`（默认 50 万）：单区域创建时预算瓦片数超限 → 拒绝（提示缩小范围/缩放级别）
  - `download.max_concurrency`（默认 4）/ `download.max_retry`（默认 3）/ `download.max_daily`（默认 10 万瓦片/天）
  - 区域创建时按 bbox×zoom 预算瓦片数并展示给管理员确认
- **瓦片元数据与覆盖（v2.0，防止"源 URL 变了还拿旧瓦片"）**：每瓦片旁写 `.meta.json`：`{source, z, x, y, etag, last_modified, downloaded_at, content_length, sha256}`；代理命中时按 `cache_ttl` 决定是否回源校验 etag/last_modified，源更新则覆盖缓存；**不同 source_key 目录隔离**，切换源不混用旧瓦片。
- 清理：`clear` 时按区域几何过滤文件删除 + 记录清理；支持全量清空。

### 9.3 维修任务状态机

```
pending(待派发) ──assign──> assigned(已派发) ──accept──> in_progress(进行中)
in_progress ──complete(记录+照片)──> done(已完成)
done ──verify──> verified(已验证) ──close──> closed(关闭)
done ──reject──> in_progress（验收驳回，附 verdict）
pending/assigned ──cancel──> cancelled（取消，必填原因）
```
- 状态流转统一走 `POST /tasks/{id}/status`，服务端校验合法性（状态机白名单）+ 权限（派发/处理/验收分离）+ **Idempotency-Key 幂等**。
- 完成时若关联 fault：`fault.status→2 待验证`（**不标已修复**）；`verify→3 已修复`；`reject→1 处理中`；`cancel` 回退故障状态（v2.0 语义，见 §5.12/§13.2）。
- 派发/状态变更写 `sys_notification`（biz_type=任务，link=/tasks/{id}）+ `sys_notification_delivery` 投递记录，手机端通知中心可见。

### 9.4 长度/插值一致性

- 落库与后端导航计算：geo_math（Python Haversine）
- 前端绘制/交互量测：Turf.js（turf.length / nearestPointOnLine / along）
- 两侧对拍用例锁口径；`cable.total_length` 保存时由后端权威计算，前端仅展示。

14. **安装/启用手动触发**：✅ **取消"启动自动安装"**——加载器只登记 NOT_INSTALLED，安装/启用/升级/卸载均由管理员在「安装模块」界面明确触发；生命周期 `不存在→已部署→未安装→已安装(停用)→已安装(启用)`，见 §2.1/§2.2/§13.1.1。
15. **模块权限 fail-closed**：✅ `module_state` 判定链 Redis→MySQL→**拒绝**（禁止 fail-open）；仅初始化向导期间特殊处理，见 §2.2/§13.1.2。
16. **正式 MigrationRunner**：✅ `sys_module_migration` 表 + `sql/migrations/{NNN}_*.sql` 逐版本执行/记录 checksum/可重入；**不承诺 DDL 整体回滚**，见 §2.2/§13.1.3。
17. **任务↔故障一致性**：✅ **complete→fault 待验证，verify→已修复，reject→处理中，cancel→回退**（完成≠修复）；任务增 `cancelled` 状态（pending/assigned 可取消，必填原因；已出库禁直接取消），见 §4.3/§5.12/§13.2。
18. **Polymorphic 任务引用**：✅ `task_requisition` 用 `task_type+task_id`，统一经 `TaskReferenceResolver`（创建校验存在/删除检查关联/查询严格双键），见 §4.3/§13.2.2。
19. **MapSourceAdapter**：✅ 每源一个 Adapter（瓦片 URL/坐标空间/业务几何与点击与 GPS 三向转换/配置校验），明确 WGS84→GCJ02/BD09 显示层转换链；**api_secret 加密、永不下发前端**，见 §5.10/§13.6。
20. **数据权限**：✅ 功能权限 + **数据范围（ALL/DEPARTMENT/OWN/ASSIGNED）**双层，服务层强制过滤（`app/core/data_scope.py`），见 §8.4。
21. **通知投递记录 + 幂等 + 锁版本 + 生命周期钩子**：✅ `sys_notification_delivery`（channel/status/idempotency_key/provider_message_id）；关键 POST 支持 `Idempotency-Key`；manifest 含 checksum/source_commit（代码漂移检测）；ModuleDef 生命周期钩子 + `sys_module.state/last_error`，见 §4.6/§14/§2.2。

## 13. 实现规格细化（开发基线补充）

> 本节为开发时可直接照做的实现规格（P0 机制契约、状态机、数据字典、接口示例、交互流程、配置示例）。代码与本节不一致视为缺陷。

### 13.1 模块插件机制实现规格（P0）

**13.1.1 ModuleDef 契约与模块包目录**

```python
# backend/app/core/modules.py
@dataclass
class ModuleDef:
    code: str                 # 唯一，如 "cable"
    name: str                 # 中文名，如 "线缆管理"
    version: str              # 插件版本号（SemVer，独立版本管理）
    router: APIRouter         # 模块全部路由；统一带 Depends(require_module_enabled(code))
    dependencies: list[str] = []   # 依赖约束（SemVer，如 ["cable>=1.2.0"]）
    audit_labels: dict[str, str] = {}   # 路由段 → 审计中文模块名（并入 _AUDIT_MODULES）
    install_sql: list[str] = []         # 安装时执行的 SQL（如 ["sql/install.sql"]）
    migrations_dir: str = "sql/migrations"   # 🆕 正式 migration 目录
    # 🆕 生命周期钩子（幂等/可重入/异常安全：异常→state=ERROR+last_error，核心继续）
    on_install: Callable | None = None
    on_enable: Callable | None = None
    on_disable: Callable | None = None
    on_uninstall: Callable | None = None
    jobs: list[Callable] = []           # APScheduler job 工厂（tick 校验 state==ENABLED）
    workers: list[Callable] = []        # 🆕 后台 worker 工厂（异常隔离）
```

目录规范（P0 起严格执行；**源码在 `backend/modules/{code}/`，运行时由管线复制到 `backend/app/modules/{code}/`**）：
```
backend/modules/{code}/        # 🆕 模块源码（开发/版本管理，git 入库）
├─ __init__.py        # ModuleDef 实例（模块唯一入口，供加载器 import）
├─ api.py             # APIRouter（所有路由挂 require_module_enabled）
├─ models.py          # SQLAlchemy 模型（表结构以模块自身 sql/* 为事实来源）
├─ schemas.py         # pydantic
├─ sql/install.sql    # 🆕 基线建表+种子（IF NOT EXISTS/INSERT IGNORE，幂等，禁止 DROP TABLE）
├─ sql/migrations/    # 🆕 版本化 migration（0001_initial.sql / 0002_xxx.sql；已发布禁改）
├─ services/          # 业务服务（如 geo_math / map_tiles / map_sources）
├─ scheduler.py       # job/worker 工厂（可选）
└─ tests/             # 模块 pytest（L2 门禁纳入，含 migration/生命周期用例）

backend/app/modules/{code}/    # 🆕 运行时安装目录（管线生成，gitignore，不手工改）
```

**加载器与生命周期（v2.0：启动不自动安装，由管理员触发）**：
```
register_modules(app)：
1. 读 sys_module（表不存在/未初始化 → 跳过并告警，保证安装向导可用）
2. 遍历 app/modules/ 下 ModuleDef（管线已就绪）：
   - 无 sys_module 记录 → 插入 state=NOT_INSTALLED（仅登记，不执行 SQL、不挂路由）
   - state=ENABLED 且依赖满足 → include_router；其余状态不挂载
   - 合并 audit_labels；注册 jobs/workers（tick 校验 ENABLED）
3. GET /health 增加 modules: [{code, name, version, state}]
```
状态机：`NOT_INSTALLED →[安装: MigrationRunner]→ INSTALLED →[启用]→ ENABLED ⇄[停用] DISABLED →[卸载]→ NOT_INSTALLED`；任何态 hook/SQL 异常 → `ERROR`（last_error/last_error_at，可重试）。

**13.1.2 状态判定（fail-closed）与错误码**

- `app/core/modules.py`：
  - `module_state(db, code) -> bool`：**仅 state==ENABLED 为 True**。判定链：Redis `wlt:module:{code}` 命中→返回；miss/异常→回源 MySQL；**MySQL 异常/无记录→False（fail-closed，拒绝模块访问）**。
  - `invalidate_module(code)`：改 state/version 后删缓存。
  - `require_module_enabled(code)` 依赖：`Depends(get_current_user)` 后校验，非 ENABLED 抛 **4009「模块未启用」**（HTTP 403）。
  - `install_module(db, code)`（管理员触发）：`INSTALLING` → MigrationRunner（install.sql + 待应用 migrations）→ on_install → `INSTALLED`；异常 → `ERROR`。
  - `enable_module/disable_module/uninstall_module`：状态迁移 + 对应 hook；**uninstall 绝不删表删数据**。
- **fail-closed 例外**：仅初始化安装向导期间（sys_module 表不存在）→ 无模块接口，天然 404/403，不阻塞安装。
- 依赖校验：SemVer 比对（`dependencies` 数组），被依赖方停用/卸载/版本不满足 → 拒绝。

**13.1.3 MigrationRunner（v2.0 正式定义，不再只靠 schema_version）**

```
MigrationRunner.run(db, module)：
1. 读 sys_module.schema_version（已应用的最高 migration 序号）
2. 若从未安装（schema_version=0 且无 0001 记录）→ 执行 sql/install.sql（基线）
3. 扫描 sql/migrations/*.sql，取序号 > schema_version 的按序执行：
   a. 计算文件 sha256 → 与 sys_module_migration 记录比对（已执行且 checksum 一致 → 跳过；
      已执行但 checksum 不一致 → **拒绝升级并告警**（防篡改））
   b. 执行该 migration（DDL 非事务，**不承诺整体回滚**）→ 写 sys_module_migration
      （module_code/version/checksum/success/executed_at）→ 成功才继续下一个
4. 全部成功 → 更新 schema_version 与 sys_module.version
```
- 每个 migration **独立、幂等、可重入**（失败记录 success=0，修好重跑跳过成功项）。
- 升级流程：`UPGRADING` → MigrationRunner → `ENABLED`；checksum 不符拒绝。

**13.1.4 模块管理接口契约**

```
GET  /modules           → {list: [{code,name, version(库内), source_version(manifest), state,
                                   dependencies, description, menu_count, perm_count,
                                   schema_version, checksum_prefix, installed_at, last_error}]}
GET  /modules/{code}    → 同上单条 + {config}（脱敏，绝不返回 api_secret）
POST /modules/{code}/install     → MigrationRunner → INSTALLED（幂等，Idempotency-Key）
POST /modules/{code}/enable      → ENABLED（on_enable）
POST /modules/{code}/disable     → DISABLED（on_disable；被依赖阻止）
POST /modules/{code}/upgrade     → UPGRADING → 应用新 migration → ENABLED（checksum 校验）
POST /modules/{code}/uninstall   → NOT_INSTALLED（不删表不删数据，on_uninstall）
```
- 权限：全部 `module:manage`；操作后 `invalidate_module` + 失效角色权限缓存。

**13.1.5 菜单/权限/定时任务联动**

- `GET /menus`：先剔除 `module_code` 非 ENABLED 模块的节点及其子级（模块状态与 §13.1.2 同一缓存）。
- 权限点：模块权限点带模块前缀；非 ENABLED 模块权限点置灰不可勾选、不产生效果（模块路由已前置拦截）。
- 定时任务/worker：job 工厂每次 tick 检查 state==ENABLED，否则 return（队列保留，启用后续跑）；hook 异常进入 ERROR 不拖垮核心。

**13.1.6 前端模块状态与守卫**

- `packages/shared`：`moduleApi`（getModules 等）；`useAuthStore` 增 `modules`/`moduleEnabled(code)`/`fetchModules()`（与 fetchMenus 并行）；`RequireModule({code,children})`：非 ENABLED → Antd `Result status="403"`「模块未启用」。
- 桌面路由：`withLayout(<RequireModule code="cable"><Page/></RequireModule>)`；硬编码兜底 `MENU` 加 `module` 字段按 `moduleEnabled` 过滤。
- 手机端：P2 引入时同样套 `RequireModule`；`moduleEnabled` 已共享。

**13.1.7 安装模块页 UI（desktop /system/modules）**

- 表格列：模块（code+名称）/ **插件版本号**（SemVer 徽标，`version`+`source_version` 对比）/ **状态 Tag**（未安装灰/已安装停用橙/已启用绿/ERROR 红）/ 依赖 / 菜单数 / 权限点数 / SQL 版本 / checksum 前 12 位 / 安装时间 / 描述
- 版本与校验：`version ≠ source_version` → 「可升级」Tag；checksum 不符 → 「代码校验失败」Tag；悬停 tooltip 显示依赖/SQL 版本/checksum
- 操作（按状态启用/禁用按钮）：安装 / 启用 / 停用 / 升级 / 卸载（二次确认不删数据）；ERROR 显示 last_error + 「重试」；依赖不满足/被依赖 → 置灰 + tooltip
- 顶部说明卡片：生命周期三态差异 + 独立版本管理 + fail-closed 安全说明

**13.1.8 边界与异常**

- `sys_module`/`sys_module_migration` 表不存在（未导入 init.sql）→ 加载器跳过、`GET /modules` 返回空，不影响初始化安装向导。
- 模块包 import 失败 → 加载器 try/except + `logger.warning`，不拖垮核心启动。
- migration 失败 → 记录 success=0 + 模块 ERROR（last_error），其他模块与核心不受影响；修复后重试跳过成功项。
- 卸载 → 重装：表与数据保留，install.sql + migrations 幂等续用，历史数据完整。
- 停用→启用：数据完整保留，重新启用即恢复功能。

### 13.2 任务状态机完整流转（task_engine，task 与 device 共用，v2.0）

**13.2.1 状态与流转**

```
pending(待派发) ──assign──▶ assigned(已派发) ──accept──▶ in_progress(进行中)
in_progress ──complete──▶ done(已完成) ──verify──▶ verified(已验证) ──close──▶ closed(关闭)
done ──reject(附verdict)──▶ in_progress
pending/assigned ──cancel(必填原因)──▶ cancelled(已取消)   # v2.0 新增
```

| 动作 | 前置状态 | 目标状态 | 权限 | 副作用 |
|---|---|---|---|---|
| assign | pending | assigned | task:dispatch | 写 assignee；通知指派对象（站内+紧急短信）；设备任务→设备维修中 |
| accept | assigned | in_progress | task:process（仅被指派者） | 通知创建人「任务已接单」 |
| complete | in_progress | done | task:process | 必填记录+照片；关联 fault→**待验证(2)**（**不直接标已修复**）；通知派发人 |
| verify | done | verified | task:verify | 必填 verdict；**fault→已修复(3)**；设备→回在用（可改）；通知处理人 |
| reject | done | in_progress | task:verify | 填 verdict 驳回原因；**fault→处理中(1)**；通知处理人 |
| close | verified | closed | task:dispatch | 终态 |
| cancel | pending/assigned | cancelled | task:dispatch（创建人/派发人） | 必填 cancel_reason；设备回退任务前状态；**已产生库存出库的任务禁止直接取消** |

- 流转校验：`task_engine.transition(task, action, actor)` 单点实现（状态白名单 + 权限 + 指派关系 + 取消约束校验），task/device 两套表各自调用；**幂等（Idempotency-Key）**。
- 编号：`WX{yyyyMMdd}{4位流水}`（device 任务 `WX-SB{...}`，`bill.rule` 前缀扩展）。

**13.2.2 领用链接（Polymorphic 引用规范化）**

- `task_requisition`：`task_type(cable/device) + task_id + requisition_id`；**所有读写经 `TaskReferenceResolver`**：
  - `resolve_task(task_type, task_id)`：按类型路由到任务表，不存在报错
  - 创建链接校验任务存在；删除/归档任务检查关联（有关联禁止物理删）
  - 查询严格 `task_type + task_id`，禁止只按 task_id
- 从任务发起领用：手机端调用任务接口 → 创建 `out_requisition`（applicant=处理人，use_reason 预填任务标题）→ 提交即出库（走 `post_stock_change()`）→ 写链接表（经 Resolver）。

### 13.5 手机端关键交互流程

**测距定位**：选择线缆 → 信息卡点「测距定位」→ 弹层输入（"从起点 350 米" / "距终点 120 米"两 Tab，实时换算）→ `POST /geo/measure` → 地图高亮插值点（脉冲圆标记）+ 信息条「距起点 350 米 / 距 2# 接头 8.5 米」→ 点「去这里」进入故障导航。

**故障导航**：故障列表/地图选故障点 → 点「导航」→ 申请定位权限 → `watchPosition` 实时定位 → 每 2s 调 `POST /geo/navigate`（或前端 Turf 本地算）→ 地图更新：用户蓝点 + 目标红点 + 沿线路径高亮 + 顶部实时卡片（直线距离/投影累计/沿线剩余）→ **距故障 <50m**：`navigator.vibrate([300,100,300])` + 语音「前方约 30 米到达故障点」（`speechSynthesis`）→ 到达（<10m）提示「已到达故障点」。

**候选线缆选择（v2.0：防"吸附到另一条平行线缆"）**：`/geo/navigate` 投影时不再只取全局最近点——在 `最近距离 × 容差系数`（默认 1.5 倍 + 固定 30m）范围内收集**候选线缆**（含目标故障线缆），结合 `用户航向 heading`（watchPosition 提供，连续两点算航向角）与**候选线缆在投影点处的走向夹角**过滤：航向与线缆走向夹角 > 60° 的线缆降权；再按「目标故障线缆优先 → 距离最近 → 夹角最小」排序返回**推荐线缆 + 投影点 + 剩余距离**；前端允许手动切换候选线缆（列表展示各候选的投影距离）。

**故障上报**：地图长按/点线缆 → 弹「上报故障」→ 选故障类型/严重度/描述 + 拍照（走 `sys_file`）→ 提交写 `cable_fault`（后端算 cumulative_distance）→ 状态待处理(红)，同步通知调度员。

## 14. 跨模块事务与一致性约束（v2.0 新增）

> 功能分散在核心与多个模块，**事务与一致性规则必须集中钉死**，避免"库存扣了任务没建成""任务完成短信失败整个回滚"这类问题。

### 14.1 事务边界分类

| 类别 | 内容 | 规则 |
|---|---|---|
| **必须同事务**（单一 DB 事务，任一步失败整体回滚） | 任务状态变更 + 状态历史/审计字段；任务完成 + 维修记录 + 关联 fault 状态联动（待验证）；领用创建（`out_requisition` + `task_requisition` 链接 + `post_stock_change()` 库存扣减）；模块 migration 单文件（非 DDL 部分） | 事务内只做 DB 写，不做外部调用 |
| **异步（绝不阻塞主事务）** | 站内通知/邮件/短信（`notify_user` 经投递表 pending 落库后异步发送）；AI 生成知识；地图瓦片下载；报表聚合 | 写入 `sys_notification`/`sys_notification_delivery` 后由后台/worker 处理；失败重试，不回滚主流程 |
| **最终一致** | 任务完成 → 通知派发人；故障上报 → 通知调度员；设备状态联动（维修中/回在用） | 允许短暂延迟；有重试与投递记录可对账 |

### 14.2 明确禁止出现的不一致

- ❌ 库存已扣、任务却没建成 → 领用创建必须与任务/库存同事务。
- ❌ 任务已 done、关联 fault 未更新 → fault 联动与状态变更同事务。
- ❌ 任务状态变更成功、通知失败导致整个回滚 → 通知走异步，不参与任务事务。
- ❌ 短信超时未知成败 → `sys_notification_delivery` 按 provider_message_id 对账 + idempotency_key 防重。
- ❌ 两个 worker 同时处理同一下载任务 → `uk(region_id,z,x,y)` + 行锁/幂等。

### 14.3 幂等（Idempotency-Key）

- 所有**关键 POST** 支持 `Idempotency-Key` 请求头（客户端生成 UUID，重试复用）：任务创建/派发/状态流转（含 complete/verify/cancel）、领用发起、故障上报、模块 install/enable/disable/upgrade/uninstall、地图下载启动、AI 生成、短信发送。
- 服务端：`idempotency_key`（biz_type+biz_id 或客户端 key）去重——重复请求返回首次结果，不重复写记录/不重复扣库存/不重复发短信。

### 14.4 审计（重点动作，v2.0 增补）

`sys_operation_log` 复用现有审计中间件（模块路由审计标签注册进 `_AUDIT_MODULES`），**新增重点审计点**（记 `before/after` JSON）：

| 类目 | 动作 |
|---|---|
| 模块 | 安装/卸载/启用/停用/升级（记版本、checksum） |
| 地图 | 地图源修改（**不记 secret 明文**）、缓存清理 |
| 任务 | 派发/转派/完成/验收/驳回/取消（记前后状态） |
| 故障/设备 | 状态修改（记前后状态） |
| 知识 | 发布/归档/AI 生成（记版本） |
| 安全 | **短信发送**（脱敏手机号）、地图源 Key 修改、AI 生成内容（记来源） |
