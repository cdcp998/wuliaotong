## 2. 模块插件机制（核心基础，先行实施）

### 2.1 设计目标

1. **新增功能不侵入核心**：线缆/设备/任务/知识库全部代码落在各自模块包内，核心只提供插件框架。
2. **生命周期严格三分**：**源码存在 ≠ 模块已安装 ≠ 模块已启用**。启动**不自动安装**；「安装」与「启用」都必须是管理员在「安装模块」界面明确触发。生命周期：`不存在 → 已部署 → 未安装 → 已安装(停用) → 已安装(启用)`，异常时进入 `ERROR`。
3. **可安装/卸载（SQL 由模块自带）**：模块包内携带 `sql/install.sql` + `sql/migrations/`，核心 init.sql 不含模块表；「卸载/移除」= **不删除任何表与数据**，仅注销，数据完整保留，重装幂等续用。
4. **安全默认 fail-closed**：模块权限判定禁止 fail-open——Redis 异常回源 MySQL、MySQL 也异常则拒绝模块访问。
5. **可升级（锁版本 + checksum）**：模块独立 SemVer；manifest 带 `checksum/source_commit/build_id`，检测代码漂移。
6. **模块异常隔离**：生命周期 hook 异常 → 记日志 + 模块进入 `ERROR`（记录 last_error），核心继续运行。
7. **不破坏现有不变量**：现有核心（库存事务、认证、审计、Redis 降级等）一行不动。

### 2.2 后端：模块注册表 + 模块包 + 插件加载器

**核心表 `sys_module`（入 init.sql）**：

```sql
CREATE TABLE sys_module (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  code        VARCHAR(50)  NOT NULL COMMENT '模块编码，如 cable',
  name        VARCHAR(100) NOT NULL COMMENT '模块名称',
  version     VARCHAR(20)  NOT NULL DEFAULT '1.0.0' COMMENT '插件版本号（SemVer）',
  state       VARCHAR(20)  NOT NULL DEFAULT 'NOT_INSTALLED'
              COMMENT 'NOT_INSTALLED/INSTALLING/INSTALLED/ENABLED/DISABLED/ERROR/UPGRADING',
  schema_version VARCHAR(20) NOT NULL DEFAULT '0' COMMENT '已执行的模块 SQL 结构版本（migration 序号）',
  depends     JSON         NULL COMMENT '依赖约束（JSON 数组，如 ["cable>=1.2.0,<2.0.0"]；SemVer 校验）',
  config      JSON         NULL COMMENT '模块配置（JSON，敏感字段脱敏）',
  description VARCHAR(255) NOT NULL DEFAULT '',
  last_error  VARCHAR(500) NOT NULL DEFAULT '' COMMENT '最近异常信息（ERROR 态）',
  last_error_at DATETIME   NULL COMMENT '最近异常时间',
  installed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_code (code)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='功能模块注册表';
```

**核心表 `sys_module_migration`（入 init.sql）**：

```sql
CREATE TABLE sys_module_migration (
  id          BIGINT AUTO_INCREMENT PRIMARY KEY,
  module_code VARCHAR(50)  NOT NULL COMMENT '→ sys_module.code',
  version     VARCHAR(50)  NOT NULL COMMENT 'migration 标识（如 0001_initial / baseline）',
  checksum    VARCHAR(64)  NOT NULL DEFAULT '' COMMENT 'migration 文件 sha256',
  success     TINYINT      NOT NULL DEFAULT 1 COMMENT '1 成功 / 0 失败',
  executed_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_module_version (module_code, version)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='模块 migration 执行记录';
```

**ModuleDef 契约**（`app/core/modules.py`）：

```python
@dataclass
class ModuleDef:
    code: str
    name: str
    version: str                  # SemVer
    router: APIRouter             # 模块全部接口（统一依赖 require_module_enabled(code)）
    dependencies: list[str] = []  # 依赖约束（如 ["cable>=1.2.0,<2.0.0"]）
    audit_labels: dict[str, str] = {}
    install_sql: list[str] = []   # 安装时执行的 SQL（如 ["sql/install.sql"]）
    migrations_dir: str = "sql/migrations"
    # 生命周期钩子签名固定：
    # on_install(db: Session, module: ModuleDef, ctx: ModuleContext) -> None
    # on_enable(db, module, ctx) / on_disable(db, module, ctx) / on_uninstall(db, module, ctx)
    on_install: Callable | None = None
    on_enable: Callable | None = None
    on_disable: Callable | None = None
    on_uninstall: Callable | None = None
    jobs: list[Callable] = []     # APScheduler job 工厂（tick 检查 ENABLED）
    workers: list[Callable] = []  # 后台 worker 工厂（异常隔离）
```

**目录结构（源码与运行时分离）**：

```

├─ modules/                      # 模块【源码】目录（git 入库）
│  ├─ base.py                    # ModuleDef 契约（开发期引用）
│  ├─ cable/
│  │  ├─ __init__.py             # cable_module = ModuleDef(...)
│  │  ├─ api.py                  # router
│  │  ├─ models.py

│  │  ├─ sql/migrations/         # 0001_initial.sql / 0002_xxx.sql（增量，禁止修改已发布）
│  │  ├─ services/geo_math.py, map_tiles.py, map_sources/
│  │  └─ scheduler.py
│  ├─ task/  knowledge/  device/

│  │  ├─ manifest.json
│  │  └─ {code}/
│  └─ core/
│     └─ modules.py              # 插件机制核心

└─ build_modules.py              # 模块安装管线
```

**安装管线**（`scripts/build_modules.py`）：
1. 扫描 `backend/modules/` 各子目录；
2. 校验结构（存在 `__init__.py` 且定义 ModuleDef）；
3. 复制到 `backend/app/modules/{code}/`；
4. 生成 `backend/app/modules/manifest.json`（含 `{code, version, schema_version, build_id, source_commit, checksum}`）；
5. 清理已删除模块的旧目录；
6. 对复制后的模块源码做 compileall 校验。

**加载器（register_modules）**：

```
1. 读 sys_module（表不存在/未初始化 → 跳过）
2. 遍历 app/modules/ 下 ModuleDef：
   - 无记录 → 插入 state=NOT_INSTALLED（仅登记）
   - state=ENABLED 且依赖满足 → include_router
   - 依赖不满足 → 置 state=ERROR，last_error="依赖不满足: ..."
   - 其余状态不挂载
3. 合并 audit_labels；注册 jobs/workers
```

**模块状态机**：

```
NOT_INSTALLED →[管理员安装]→ INSTALLED →[启用]→ ENABLED ⇄[停用]→ DISABLED
任何态 →[hook/SQL异常]→ ERROR（记录 last_error，可重试）
ENABLED →[升级]→ UPGRADING →[migrations完成]→ ENABLED（**升级后需重启后端进程加载新代码**，管理界面升级后强制提示「请重启后端使新代码生效」）
DISABLED/INSTALLED →[卸载]→ NOT_INSTALLED（不删表不删数据）
依赖不满足 → ERROR（写 last_error=缺失依赖列表；**不允许"不挂载但 state=ENABLED"的静默不一致**；依赖恢复后重新启用）
```

**fail-closed 判定**：

```
module_enabled(db, code)：
    Redis wlt:module:{code} 命中且 state==ENABLED → True
    Redis miss/异常 → 回源 MySQL sys_module.state==ENABLED → True
    MySQL 异常/无记录 → False（拒绝模块访问）
```

**MigrationRunner（幂等可重入）**：

> **约定**：install.sql 作为 `baseline` 纳入 `sys_module_migration` 记录（version='baseline'），并计算 checksum。每个增量 migration 文件**只能包含一条 DDL 语句**（或使用工具函数保证幂等）。**migrations 从 0001 起只含增量，0001 不得重复建基线已建的表**；**禁止修改已发布的 migration 文件**（checksum 拦截）。所有 migration SQL 必须使用核心提供的工具函数：
> ```python
> from app.core.migration_utils import column_exists, index_exists, table_exists
> ```
> 示例：
> ```sql
> -- 0002_add_xxx.sql
> ALTER TABLE cable ADD COLUMN xxx VARCHAR(50) NULL;
> ```
> 前提：在 Python 执行前先调用 `column_exists('cable','xxx')` 判断，若无则执行；或者迁移 SQL 本身通过存储过程/条件判断保证幂等（MySQL 8 不支持 `ADD COLUMN IF NOT EXISTS`）。  
> **推荐**：每个 migration 文件由 Python 函数执行，函数内使用工具函数检查后执行 DDL，并将 checksum 记录到 sys_module_migration。
>
> **失败恢复策略**：migration 失败记录 `success=0` + 模块 `ERROR`（last_error）；修复 = **追加一个幂等新 migration**（推荐），或**仅当该失败文件从未在任何环境成功应用时**整体重写为幂等后重跑（否则与已应用环境 checksum 冲突）。

```
MigrationRunner.run(db, module)：
1. 读 sys_module.schema_version
2. 若从未安装（schema_version=0 且无 baseline 记录）→ 执行 install.sql，记录 baseline checksum
3. 扫描 migrations/*.sql，取序号 > schema_version 的按序执行：
   a. 计算 sha256，与 sys_module_migration 已执行记录比对（已执行且 checksum 一致 → 跳过；不一致 → 拒绝升级）
   b. 执行该 migration（调用模块提供的函数）→ 写 sys_module_migration（version/checksum/success）
   c. 成功才继续下一个
4. 全部成功 → 更新 schema_version 与 sys_module.version
```

**核心提供 Migration 工具**：`app/core/migration_utils.py` 包含 `table_exists`、`column_exists`、`index_exists`、`execute_safe_alter` 等。

### 2.3 前端：模块状态 + 路由守卫 + 菜单过滤

- 共享层新增 `moduleApi.getModules()`；`useAuthStore` 增加 `modules` 与 `moduleEnabled(code)`；登录后与菜单一起拉取。
- 路由守卫 `RequireModule({ code })` 组件：非启用渲染"模块未启用"占位。
- 菜单：后端菜单已过滤；硬编码兜底 MENU 增加可选 `module` 字段，`menuVisible` 同时校验模块启用。
- 模块页面组织在 `apps/{desktop,mobile}/src/modules/{code}/`，路由在 `main.tsx` 懒加载注册。

### 2.4 系统管理「安装模块」界面

- 路由 `/system/modules`，权限 `module:manage`。
- 列表列：code/名称/插件版本号（SemVer 徽标）/状态 Tag/依赖/菜单数/权限点数/SQL 版本/checksum 前缀/安装时间/描述。
- 版本漂移提示：`version ≠ source_version` → 「可升级」；checksum 不符 → 「代码校验失败」。
- 操作：安装/启用/停用/升级/卸载；卸载二次确认「不删除任何表与数据」；ERROR 显示 last_error + 重试。
- 依赖不满足/被依赖引用 → 按钮置灰 + tooltip。
- **「重新扫描模块源码」按钮（v2.1）**：只读触发 `build_modules.py --check-only`（重扫 `backend/modules/`，比对 manifest 与库记录，**不改数据库**），返回新模块/版本变化/代码漂移列表供升级前预检。

## 5. 关键架构决策

### 5.1 空间数据：MySQL 单库 + 应用层 Geo

- 线缆 geometry 存 GeoJSON JSON 列；cable_point 存逐点坐标+累计距离；距离/插值/最近点全部由 `backend/app/modules/cable/services/geo_math.py` 实现。
- 不引入 PostGIS，保持单库事务一致性。

### 5.2 地图引擎：Leaflet

- react-leaflet，GeoJSON 矢量叠加，Turf.js 交互计算。

### 5.3 坐标系：统一 WGS84

- 存储与后端计算一律 WGS84；后端接口返回 WGS84。
- 前端根据当前地图源 `coordinate_space` 在显示层转换（`geo.ts`），后端不负责业务几何显示转换。
- 地图源瓦片 URL 由后端瓦片代理生成（代理持有 key），不暴露给前端。

### 5.4 瓦片缓存：后端瓦片代理

- 前端请求 `/map/tile/{source}/{z}/{x}/{y}`（归 cable 模块）。
- 磁盘缓存优先，未命中抓在线源落盘；批量下载走 Redis 队列 + worker。
- 容量保护：`cache.max_size`、`region.max_tiles`、`download.max_daily`。
- 每瓦片旁写 `.meta.json` 记录 etag/last_modified，按 cache_ttl 校验更新。
- 地图源与缓存管理全部在 cable 模块内。

### 5.5 测距定位 / 故障导航

- geo_math 实现 Haversine、累计距离插值、最近点投影、剩余距离。
- 前端 Turf.js 实时预览，后端权威计算落库。
- 导航时由前端 `watchPosition` 调 `/geo/navigate`，后端返回投影与剩余距离。
- 候选线缆选择：考虑航向夹角过滤，避免吸附平行线缆。

### 5.6 手机端提醒

- vibrate + speechSynthesis；WebSocket/SSE 为 P2 可选。

### 5.7 知识库 AI 生成

- 复用 LLMClient + RAG-lite；异步生成任务，落草稿待人工审核。
- 生成任务状态模型（定稿）：**`knowledge_generate_task` 表**（见 §4.4），`POST /knowledge/generate` 异步入队返回 task_id，前端轮询 `GET /knowledge/generate/{task_id}` 获取结果（success 返回 article_id / failed 返回 last_error 可重试）；由 knowledge 模块后台 worker 消费（复用 `ModuleDef.workers`，tick 校验 ENABLED），超时上限 120s、LLM 失败重试 ≤2。

### 5.8 设备管理

- 设备台账 CRUD + 地图标记叠加层。
- 设备维修任务复用通用任务状态机核心（task_engine），独立建表。
- 设备生命周期：在用⇄维修中⇄闲置→报废；维修中禁止报废；创建设备维修任务自动置维修中；任务完成/cancel 时按回退规则处理（记录 previous_status）。

### 5.9 通知三渠道

- 站内/邮件/短信统一 `notify_user(...)` 分发，写 sys_notification_delivery。
- 通知发送 worker **`app/services/notify/worker.py`**（核心服务，随核心启动，独立于任何模块）处理 pending 投递记录；单条失败仅标 failed + retry_count+1（≤3），异常隔离，模块停用不影响通知投递。
- 短信客户端抽象 `SmsClient`，支持阿里云/腾讯云/容联云/通用 HTTP。
- 幂等：`idempotency_key`，防重复发送。

### 5.10 多地图源（MapSourceAdapter）

- 地图源配置存 cable 模块 `sys_module.config`。
- 每个源实现一个 Adapter（`backend/app/modules/cable/services/map_sources/base.py` + 前端 `geo.ts` 同构）。
- 后端瓦片代理负责生成瓦片 URL 并缓存；前端根据源 `coordinate_space` 做显示层转换。
- api_secret 加密存储，`/map/sources` 接口脱敏，永不下发。

### 5.11 地图叠加层选择

- 地图组件内置叠加层开关（线缆/故障/设备/标记点/缓存区域/用户位置），各层独立显隐。

### 5.12 通用任务状态机核心（task_engine）

- 核心服务 `backend/app/core/task_engine.py`（不建表，纯服务）：状态机校验、流转、通知、记录、领用链接。
- 提供回调钩子 `transition_callbacks: list[Callable] = []`，允许 device 模块注入设备状态联动逻辑。
- 状态机：`pending → assigned → in_progress → done → verified → closed`；`done→in_progress`（验收驳回）；`pending/assigned → cancelled`。
- 任务↔故障一致性：complete→fault 待验证(2)，verify→已修复(3)，reject→处理中(1)，cancel 回退。

## 9. 技术实现要点

### 9.1 geo_math.py

```python
R = 6371008.8  # 与 turf 一致
def haversine(lat1, lng1, lat2, lng2) -> float
def cumulative_distances(points) -> list[float]
def interpolate_by_distance(points, dists, target) -> (lat, lng)
def project_point_to_line(p, a, b) -> (lat, lng, t)
def project_to_polyline(points, p) -> (nearest_pt, cum_dist)
def remaining_distance(from_cum, to_cum) -> float
```

### 9.2 瓦片下载 worker + 缓存容量保护

- worker 循环：从队列取任务 → 校验 ENABLED → 抓取 → 落盘 → 更新统计。
- 并发限流、幂等、断点续传。
- 容量保护：`cache.max_size`、`region.max_tiles`、`download.max_daily`。
- 瓦片元数据 `.meta.json`，按 etag/last_modified 更新。
- **瓦片清理统一入口（v2.1）**：封装 `backend/app/modules/cable/services/tile_cache.py`，集中实现「扫描删除文件 + 清理 `.meta.json` + 更新 region/download 统计」；**下载 worker 与清理接口共用同一入口与进程锁**，避免并发竞争（正在写的瓦片不删/删后幂等重抓，靠 `uk(region_id,z,x,y)` 兜底）。

### 13.2 任务状态机完整流转（task_engine）

**状态与流转**：

```
pending(待派发) ──assign──▶ assigned(已派发) ──accept──▶ in_progress(进行中)
in_progress ──complete──▶ done(已完成) ──verify──▶ verified(已验证) ──close──▶ closed(关闭)
done ──reject──▶ in_progress
pending/assigned ──cancel──▶ cancelled
```

**动作副作用**：

| 动作 | 前置 | 目标 | 权限 | 副作用 |
|---|---|---|---|---|
| assign | pending | assigned | task:dispatch | 写 assignee；通知；设备任务→维修中 |
| accept | assigned | in_progress | task:process（被指派者） | 通知创建人 |
| complete | in_progress | done | task:process | 必填记录+照片；fault→待验证(2)；通知派发人 |
| verify | done | verified | task:verify | 填 verdict；fault→已修复(3)；设备回退/在用 |
| reject | done | in_progress | task:verify | 填 verdict；fault→处理中(1) |
| close | verified | closed | task:dispatch | 终态 |
| cancel | pending/assigned | cancelled | task:dispatch | 必填原因；设备回退；已出库禁止直接取消（需先冲销领用） |

**唯一活跃任务约束**：同一 fault 最多一个非终态任务，创建时校验（应用层校验 + 表级唯一索引兜底）。

**领用链接**：`task_requisition` 经 `TaskReferenceResolver` 校验任务存在；取消已出库任务时，需先冲销出库单再取消。

**task_engine 回调钩子**：

```python
def transition(task, action, actor, callbacks: list[Callable] | None = None, **kwargs):
    # 执行状态校验、写库、审计
    # 调用 callbacks（device 模块传入设备状态联动逻辑）
    for cb in callbacks or []:
        cb(db, task, action, actor, **kwargs)
```

## 14. 跨模块事务与一致性约束

### 14.1 事务边界

| 类别 | 内容 | 规则 |
|---|---|---|
| 必须同事务 | 任务状态变更 + 审计；任务完成 + 维修记录 + fault 状态联动；领用创建 + 库存扣减 + 链接表；模块 migration 单文件 | 单一 DB 事务，无外部调用 |
| 异步 | 通知发送、AI 生成、瓦片下载 | 写入投递/生成任务后异步处理 |
| 最终一致 | 通知送达、设备状态联动 | 允许延迟，有重试对账 |

### 14.2 禁止出现的不一致

- 库存已扣任务未建成 → 同事务。
- 任务已完成 fault 未更新 → 同事务。
- 通知失败导致任务回滚 → 通知异步。
- 短信超时未知 → 投递记录对账。
- 重复下载同一瓦片 → uk + 行锁。

### 14.3 幂等

- 所有关键 POST 支持 `Idempotency-Key`。
- 服务端去重，重复请求返回首次结果。

### 14.4 审计

重点审计点：模块安装/卸载/启停/升级、地图源修改（不记 secret 明文）、任务流转、故障/设备状态修改、知识发布、短信发送（脱敏）。

## 附：开发规范补充（模块开发）

1. 所有新功能模块化，源码写 `backend/modules/{code}/`。
2. 运行时目录 `backend/app/modules/` 由管线生成，禁止手工修改。
3. 模块 SQL 自带 `sql/install.sql` + `sql/migrations/`，禁止把模块表加入核心 init.sql。
4. 卸载绝不删表删数据；模块 SQL 禁止 `DROP TABLE`。
5. 生命周期钩子必须幂等、可重入、异常安全。
6. Migration 必须使用核心工具函数保证幂等；每个 migration 文件只包含一条 DDL 或由 Python 函数检查后执行。
7. 模块间禁止跨模块 import models；跨模块数据访问走 API 或共享 core 层。
8. 模块权限点、菜单必须带 module_code。
9. 跨模块 API 变更必须主版本升级并更新依赖方 depends。
10. 模块升级完成后必须**重启后端进程**才加载新代码（管理界面强制提示）。
11. 瓦片/缓存清理统一走 `tile_cache.py` 入口（worker 与清理接口互斥）。
